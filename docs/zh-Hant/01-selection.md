# 01｜按場景選型，而不是按熱門程度選型

## 先分清三個層次

- **開發工具／harness**：幫工程師閱讀、修改與驗證 repository。Pi 放在這一層。
- **應用框架／執行編排**：你用它建造自己的服務。LangGraph 與 Pydantic AI 主要在這一層比較，但抽象層級不同。
- **架構模式**：固定工作流程、單一工具型 agent、Agentic RAG、graph-based retrieval、多 agent 協作。這些不是可以直接用同一張產品排行榜排名的套件。

一個系統可以採用多個層次，但每多一層都要說明它解決了什麼已確認的問題。

## 場景與選擇

下表的「優先評估」是工程建議，不是效能測量結果。

| 實際工作 | 優先評估 | 為什麼 | 何時不用／必查代價 |
|---|---|---|---|
| 定期讀取資料、固定規則分類、產生報表 | 一般程式／工作流程 | 路徑已知，易測試、對帳與維護 | 不必引入模型來重新決定已知規則 |
| 文件抽取成固定欄位，供後端處理 | 型別明確的模型整合；可評估 Pydantic AI | 資料契約是主要問題 | 結構通過驗證不代表內容真實；仍要對原文 |
| 跨步驟任務需中途停下、人工核准、復原 | 可評估 LangGraph | 需求集中在狀態與流程編排 | 短小流程可能不值得增加狀態模型及持久層 |
| 工程師要修改程式、跑測試、檢查差異 | 可評估 Pi coding agent | 任務以 repository 與開發工具為中心 | 不能把開發工具直接當成企業權限後端 |
| 查一組文件並給可核對的答案 | 固定檢索流程作為基準 | 先衡量搜尋與證據品質 | 沒有複雜路由需求時不必加入 agent |
| 同一問題需要依結果選文件、SQL 或 API | 限定工具與步數的 Agentic RAG | 查詢路徑取決於中間證據 | 工具選擇增加延遲、成本與錯誤路徑 |
| 需要追蹤專案、系統、文件間的關係 | SQL／明確關係查詢，再評估圖譜檢索 | 問題關心關係與跨文件連結 | 圖抽取錯誤、索引更新與衍生資料權限須量測 |
| 子任務能獨立驗收且確有並行價值 | 才評估多 agent | 分工有可測量收益時才增加協調 | 多個角色名稱不會自動提高可靠性 |

## 官方事實與我們的判斷

LangGraph 官方把它定位為狀態型、長時間任務的低層編排工具；持久化、恢復與人工介入是其文件主題。這支持「評估狀態編排」的建議，不等於選用後已具備企業可靠性。[官方概覽](https://docs.langchain.com/oss/python/langgraph/overview)

Pydantic AI 文件涵蓋型別、輸出、依賴與工具。這支持以 Python 資料契約為中心的候選定位，不能推出它在你的任務上更準確或更便宜。[官方概覽](https://pydantic.dev/docs/ai/overview/)

Pi 官方定位為可擴充的 agent harness，提供互動與程式整合方式。這是另一種任務層次，不能只數功能就和後端編排框架比較。[官方網站](https://pi.dev/)

## 用一張需求單淘汰不適合的選項

在安裝候選框架前，填寫：

1. 使用者是誰？身分由哪個可信系統提供？
2. 任務的輸入、輸出、可存取資料與禁止動作是什麼？
3. 哪些步驟固定，哪些真的需要模型決定？
4. 是否必須跨程序中斷恢復？可否接受人工重跑？
5. 哪些動作有外部副作用？逾時後怎麼確認是否已完成？
6. 驗收資料、錯誤分類、延遲／費用上限由誰定義？
7. 維護者能否理解、測試並替換所選方案？

若答案還空白，先補需求；不要把缺乏需求變成安裝更多框架的理由。固定同一任務，保留無框架基準，每輪只納入最多兩個真正滿足需求的候選。選擇保留基準、延後或淘汰都算有效結論。
