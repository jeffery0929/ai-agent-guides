# 05｜一般 RAG、Agentic RAG 與 GraphRAG 怎麼選？

[English — 主要版本](../en/05-retrieval-design.md) · 繁體中文翻譯
本篇是架構設計工作坊，沒有已部署模型、向量資料庫或圖譜索引。目標是產出可以實作與驗收的設計，而不是堆疊名詞。

## 用三種企業內部問題來區分

1. 「這項系統存取申請的核准流程是什麼？」先以詞彙／向量檢索、來源引用和拒絕回答做基準。
2. 「這個專案的文件、目前工單狀態與系統負責人是否一致？」資料跨文件與結構化系統，可能需要工具路由；評估限定的 Agentic RAG。
3. 「哪些專案透過共享系統互相依賴？跨部門的主要議題是什麼？」評估明確關係資料與圖譜方法；不能僅因問題很長就斷定需要 GraphRAG。

Microsoft GraphRAG 是特定的圖譜索引與檢索方法，不能把所有「使用圖」的設計都說成已實作 Microsoft GraphRAG。[官方文件](https://microsoft.github.io/graphrag/)

## 步驟一：先定義資料與問題

建立小型、獲准的文件集合，保留來源 ID、版本、定位與存取規則。另建立問題集，區分精確欄位、單段程序、跨文件關係、全體概述與無法回答的問題。

先標記每題可支持答案的原文，並保留未參與調整的驗收題。若沒有可靠答案標註，先不要公布檢索準確率。

## 步驟二：先做可以解釋的基準

文件解析 → 片段與 metadata → 權限篩選 → 檢索／重排 → 回答或拒絕 → 引用檢查。

分開量測「來源是否找對」與「答案是否被來源支持」。解析錯字或表格邊界錯誤不能靠改 agent 提示保證修好。無資料與無權限可以對使用者採一致回應，避免洩漏隱藏文件是否存在。

## 步驟三：只有基準解不好的問題才擴充

### Agentic RAG

增加一個決策點，選擇允許的文件、SQL 或 API 工具。先限制工具為唯讀，每個回傳有來源與版本；定義步數、費用與停止條件。測試錯誤工具、循環、不可信工具文字與工具逾時。若多出來的決策沒有改善相同題目的成果，移除它。

### 圖譜檢索

先確認關係能否由既有資料庫直接查到。需要抽取時，保留關係的來源與不確定性；錯誤連結會讓推論看似合理卻沒有依據。若做群集或跨文件摘要，摘要與快取也有權限與更新生命週期，不能只過濾最後引用。

把「找到直接關係」與「對整個文件集合產生概述」分開測。比較新增索引成本、更新時間、檢索品質與最終答案支持率；不要預設圖譜一定更好。

## 步驟四：把設計交付物寫清楚

- 資料流與信任邊界圖。
- 問題類型與各路徑的選擇理由。
- 來源、版本、解析、引用與權限契約。
- 無證據、工具故障、舊資料、撤權、刪除與重新索引測試。
- 固定的驗收集、人工核對方式、成本與延遲預算。
- 不適用情況與回退到基準的條件。

這些文件完成後，才有條件說明「這個架構值得實作比較」。要聲稱系統可用，仍須補程式、執行結果與真實資料驗收。

## 審查補充

以上是待驗證的設計建議，不是 benchmark 結果。權限過濾的具體位置與方式須依索引後端測試，但未授權資料不得進入重排器或生成模型。無資料與無權限採一致訊息只能降低部分存在性洩漏，不能單獨消除時間差、日誌等旁路。
