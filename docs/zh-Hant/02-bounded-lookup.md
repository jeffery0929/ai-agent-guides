# 02｜建立可檢查的工具執行邊界

## 目標與場景

企業內部同事詢問系統存取流程。程式只能讀取允許的合成文件，回傳原文片段，並記錄每次工具執行。沒有證據時不能憑空完成；失敗與重試也必須可見。

這不是完整 AI agent。本篇用**預先寫好的工具提案**代替模型，先學會控制執行。之後即使改接模型，工具閘道也不應盲目信任模型輸出。

## 1. 準備與執行

使用 Python 3.11+，在 repository 根目錄執行：

```sh
python3 examples/bounded_lookup/run.py
python3 -m unittest discover -s tests -v
```

不用安裝套件，不用 API Key，不發出網路請求。測試過的確切 Python 版本見 [驗證紀錄](../../evidence/VALIDATION.md)。

## 2. 先讀契約，再讀迴圈

程式：[run.py](../../examples/bounded_lookup/run.py)。資料包含兩筆虛構程序；`it` 與 `finance` 是本機角色模擬。`role` 是測試的設定，不是經過認證的使用者身分。

提案只能具有 `tool` 和 `args` 兩個鍵。例如：

```json
{"tool": "search", "args": {"query": "access"}}
```

- `search` 只接受 `query`，使用去除頭尾空白、轉小寫後的精確關鍵字匹配。
- `finish` 只接受空物件；不能夾帶一段模型自己宣稱的答案。
- 查詢不得為空，也不得超過 120 字元。
- 只允許 `search` 與 `finish`，沒有寄信、寫檔或執行 shell 工具。

加入額外的 `role` 參數不會提升權限，而是被拒絕。這教的是工具契約，不是完整注入防禦。

## 3. 跟一次正常執行

```mermaid
flowchart LR
    P[工具提案] --> V[驗證工具與參數]
    V --> R[先按模擬角色篩選資料]
    R --> S[精確關鍵字查詢]
    S --> E[保存原文引用與事件]
    E --> F[finish 檢查是否有證據]
```

`normal.status` 應為 `COMPLETE`，引用 ID 為 `IT-001`；引用原文必須與程式中的文件完全一致。成功不是模型說「完成」，而是程式走到合法結束點且持有查詢結果。

## 4. 主動製造失敗

腳本也會輸出以下情境：

| 情境 | 預期結果 | 你應檢查的事 |
|---|---|---|
| `retry` | `COMPLETE` | trace 依序包含 `TOOL_UNAVAILABLE`、`SEARCH`、`FINISH` |
| `role_filtered` | `NO_EVIDENCE` | finance 角色查 access 不得拿到 IT 文件引用 |
| `loop_stopped` | `BUDGET_EXHAUSTED` | 最多記錄四步；不回傳尚未完成的引用 |

本篇的故障是注入的工具不可用事件，不是真實 HTTP timeout。下一次明確提案才能重試；不會偷偷重跑無限次。

## 5. 閱讀測試與反例

開啟 [test_lookup.py](../../tests/test_lookup.py)。先看以下三個容易漏掉的反例：

1. 搜尋成功後改查不存在的字，舊引用必須清空。
2. 只搜尋而未 `finish`，狀態必須是 `INCOMPLETE`。
3. 提案中塞入 `send_email`，即使參數合理也必須拒絕。

練習：在 `DOCUMENTS` 加一筆第三部門資料，先設計應允許與應拒絕的查詢測試，再修改角色契約。驗收不是「多一筆能搜到」，而是既有隔離與無證據行為都不退步。

## 6. 什麼時候適合保留這種寫法？

工具少、流程短、狀態簡單且不需跨程序恢復時，直接寫清楚的程式有助於讀懂每個判斷。當真的需要長時間等待、持久化、分支和人工介入，才進入 [同題比較](03-framework-workshop.md)。

## 本篇沒有證明的事

沒有模型選工具、語意檢索、真實身分／ACL、程序中斷恢復、並行隔離、外部寫入或真實成本量測。步數上限也不是牆鐘超時控制；真實阻塞工具需要另外的執行超時與取消設計。接模型時必須重新處理輸出解碼、工具結果不可信、上下文洩漏、請求費用與真實問題的答案評估。
