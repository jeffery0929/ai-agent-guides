# 03｜用同一個任務比較框架

[English — 主要版本](../en/03-framework-workshop.md) · 繁體中文翻譯
這是逐步的實驗設計教學；本篇尚未執行 LangGraph 或 Pydantic AI SDK，不提供未核對版本的安裝與 API 範例。可執行基準見 [第 02 篇](02-bounded-lookup.md)。

## 任務：內部服務請求的分類與處理草稿

輸入是一則合成服務請求、一組可存取文件與可信系統提供的使用者身分。輸出是分類、來源、待確認資訊與處理草稿。初期只產生草稿，不寫入正式工單系統。

固定四個步驟：驗證請求 → 查允許的來源 → 產生草稿 → 驗證分類與來源。先判斷這四步是否已足夠；不要先把每一步改成一個 agent。

## 第一步：凍結公平比較契約

所有候選使用相同文件快照、問題集、工具與評分準則。有模型的實驗還須記錄同一模型識別、提示版本、參數、重試策略和費用上限。不得讓一個候選讀更多文件或用更強模型，再把差異歸功於框架。

| 驗收面向 | 如何測 | 失敗反例 |
|---|---|---|
| 業務結果 | 人工核對分類、必填欄位與草稿是否可用 | JSON 合法，但分類或內容錯誤 |
| 來源 | 引用能解析到正確版本，且支持具體主張 | 引用存在但與回答無關 |
| 權限 | 使用兩個身分分別查相同問題 | 未授權文字先進了模型，最後才隱藏 |
| 失敗處理 | 工具不可用、無資料、輸出不合法、取消 | 把失敗當成空字串後繼續宣布成功 |
| 資源 | 記錄每次執行步數、請求數、延遲與實際費用 | 只公布成功案例，漏算重試 |

門檻必須先依任務風險與使用者需求確定。本教學不虛構通用的「95% 準確就能上線」。

## 第二步：提出可反駁的候選假設

### A. 直接實作

把狀態與錯誤放在明確函式中。假設：固定流程無須框架即可達標，維護者能理解全部分支。

實作功課：將第 02 篇的 scripted proposal 替換為隔離的模型介面，保留工具驗證；新增分類結果與來源支持的人工標註。若沒有恢復需求，不為比較而新建資料庫。

### B. Pydantic AI

官方提供型別化輸出、依賴與工具整合。**候選假設**：對 Python 後端的結構化草稿任務，能減少手工資料驗證與整合程式碼，同時維持原有拒絕與來源規則。[官方文件](https://pydantic.dev/docs/ai/overview/)

實作功課：定義分類／來源／待確認欄位契約，把資料存取封裝在工具中；分別測「型別正確但事實錯誤」與「工具回傳拒絕」。不要把 schema 驗證當成內容正確性。

採納條件：相同任務品質與故障測試下，維護成本改善足以抵銷依賴與升級成本。若只能換寫法，沒有可說明的收益，就保留基準。

### C. LangGraph

**候選假設**：若新增「等待人工核准，程序重啟後再繼續」的真實需求，狀態編排與 checkpoint 值得評估。[概覽](https://docs.langchain.com/oss/python/langgraph/overview)

實作功課：畫出查詢、草稿、等待與完成的狀態轉移；選定持久化後端，再測中途終止與恢復。記憶體 checkpoint 不會跨程序重啟保存。[持久化文件](https://docs.langchain.com/oss/python/langgraph/persistence)

人工審批必須綁定特定草稿版本與動作。恢復可能重新執行部分節點邏輯，副作用需要冪等或對帳設計，不能以「有 checkpoint」推論恰好一次。[interrupts 文件](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 第三步：限定實驗規模

一般分類草稿先測直接實作與一個適合的型別工具。只有恢復／審批需求成立時才納入狀態編排候選。每輪保留基準，最多兩個候選，不因文章提到三個方向就同時安裝全部。

## 第四步：保存可重現的結果

每次記錄 source commit、確切套件與鎖檔、Python 版本、工具資料快照、測試識別、模型設定、原始失敗、費用與延遲。可用 `PASS / FAIL / NOT_RUN / NOT_APPLICABLE`，並附理由；不能把 NOT_RUN 當 PASS。

結論至少包含：採納／保留基準／延後／淘汰、證據、維護代價、遷移路徑。這是一個工程決策，不是框架推薦排行榜。
